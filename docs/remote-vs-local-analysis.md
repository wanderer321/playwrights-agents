# 远程 MCP Server vs 本地实现 — 差异分析报告

> 声明：远程 MCP Server 是闭源的黑盒，以下分析全部基于使用行为反推，不代表对方实际实现。

---

## 1. 我们能确定的事实

以下是通过实际使用 Playwright Agents MCP 观察到的确定行为：

| 观察项 | 证据 |
|--------|------|
| Planner 会打开浏览器访问页面 | 运行期间能看到浏览器被启动并导航到项目页面 |
| Planner 产出 Markdown 格式的测试计划 | 直接输出了带 `## Suite:`、`### TC-XXX` 的 markdown |
| Generator 产出可执行的 `.spec.ts` 代码 | 生成了包含 `import { test, expect }` 的有效 Playwright 代码 |
| Generator 引用了页面中的元素 | 代码里的 selector（role、text）与实际页面元素匹配 |
| Healer 会在失败处暂停并抓取页面状态 | 观察到 `test_debug` 行为，浏览器停在失败位置 |
| Healer 能自动编辑测试文件 | 测试文件内容被修改后重新执行 |
| 三个 Agent 的工作需要串联编排 | Plan → Generate → Execute → Heal 是顺序依赖的 |

## 2. 我们不确定的事情（只能推测）

| 问题 | 推测 | 不确定程度 |
|------|------|-----------|
| 对方用的是什么 LLM？ | 大概率是 Claude（因为 Anthropic 出品的工具 + 代码理解质量非常高） | 低 |
| MCP Server 本身是单体还是微服务？ | 推测是单体进程，内部用子模块隔离 3 个 Agent | 中 |
| Planner 如何理解项目结构？ | 推测：先浏览器抓页面快照 → 提取所有交互元素 → 喂给 LLM 分析 | 中 |
| Generator 如何将测试计划转代码？ | 推测：解析 markdown → 对每个用例让 LLM 生成代码 → 写文件 | 中 |
| Healer 如何决定修复方案？ | 推测：错误日志 + 页面快照 → LLM 分析根因 → 生成代码 diff → 应用 | 中 |
| 是否有内置的测试结果缓存？ | 不确定。没有观察到明显的缓存行为 | 高 |
| Agent 之间是否有状态共享？ | 推测通过临时文件或内存变量共享（例如 plan 的 markdown 文件） | 高 |

## 3. 能力对比矩阵

| 能力维度 | 远程 MCP Server | 本地实现 | 差距 |
|---------|---------------|---------|------|
| **LLM 代码理解** | Claude（顶尖水平） | 阿里云百炼 glm-5（中等） | **大** — 本地 AI 对复杂代码逻辑的理解、边界情况推断明显弱于 Claude |
| **选择器生成准确度** | 高 — 能精确生成 role/text 选择器 | 中 — 可能生成错误或不精确的选择器 | **中** — 取决于 AI 模型对页面结构的理解 |
| **测试计划完整性** | 全面 — 覆盖正常路径、边界、异常 | 较基础 — 可能遗漏边缘场景 | **中** |
| **失败根因分析** | 深入 — 能判断"选择器过期 vs 逻辑变更 vs 时序问题" | 较浅 — 能识别常见模式但深度不够 | **大** |
| **自动修复成功率** | 高 — 能生成正确的代码修复 | 中低 — 可能给出不准确的修复建议 | **大** |
| **执行速度** | 有网络延迟（MCP HTTP 调用） | 无网络延迟（本地直接执行） | **本地更快** |
| **文件读写能力** | 受限（通过 MCP 协议间接操作） | 直接文件系统访问 | **本地更强** |
| **浏览器操作** | 通过 Playwright MCP 工具 | 通过 Playwright MCP 工具 | **相同** |
| **项目代码可见性** | 只能通过 `browser_navigate` 访问页面 | 直接读取源代码文件 | **本地更强** |
| **调试能力** | 通过 `test_debug` + `browser_snapshot` | 通过 Playwright 原生调试 | **相同** |

## 4. 关键差异深度分析

### 4.1 AI 模型差异是最大短板

本地实现与远程 MCP 的差距中，**80% 来自 AI 模型能力的差距**。

远程 MCP（Claude）的优势：
- 能理解复杂的前端框架逻辑（React 状态管理、路由跳转）
- 能推断出测试需要覆盖的边界情况
- 在 Healer 场景中，能准确区分"选择器过期"和"应用逻辑变更"
- 生成的代码几乎不需要人工修改

本地（阿里云百炼 glm-5）的劣势：
- 对复杂代码上下文的保持能力较弱
- 在生成 Playwright 选择器时可能不够精确
- 失败诊断的深度和准确度不够

**缓解方案**：本地 AI Gateway 设计为可切换提供商，用户可以换成更强的模型（如通过 OpenAI 兼容接口接入 Claude API 或其他模型）。

### 4.2 MCP 协议实现差异

| 远程 MCP | 本地 MCP |
|---------|---------|
| 基于标准 MCP 协议（JSON-RPC over HTTP/SSE） | 自定义 HTTP API（RESTful） |
| 需要复杂的握手和 capability negotiation | 直接调用，无额外协议开销 |
| 工具调用需通过 `tools/call` 端点 | 每个 Agent 有独立 API 路由 |
| 通过 `list_tools` 暴露能力清单 | 相同，有 `/api/mcp/status` 返回工具列表 |

实际影响：**对最终用户来说差异很小**。MCP 协议主要是服务间通信的规范，对功能没有本质影响。

### 4.3 工作流编排差异

远程 MCP 将编排逻辑放在客户端（Claude Code 根据用户意图选择调用哪个 Agent），而本地实现将编排逻辑放在了服务端（`TestRunner.run_full_pipeline` 按固定顺序调用 4 个 Agent）。

远程：
```
用户:"跑测试" → Claude Code 决定: 先调 Planner → 用户确认计划 → 调 Generator → 调 Executor → 调 Healer
```

本地：
```
用户点"开始测试" → TestRunner: Planner → Generator → Executor → Healer (全自动串联)
```

本地更自动但缺乏用户确认环节，远程更灵活但需要用户参与决策。

### 4.4 测试修复能力差异

这是**差距最大的环节**。Healer 需要：
1. 理解错误信息
2. 理解当前页面状态
3. 对比测试代码的预期
4. 判断根因
5. 生成修复代码
6. 验证修复

每一步都高度依赖 AI 的理解能力。远程 Claude 在这方面的表现明显优于本地使用的模型。

## 5. 总结

```
                    远程 MCP Server        本地 MCP Server
                        │                        │
  AI 理解能力  ─────────┼──────── 强 ────   中等 ──┼──── 可切换模型改善
  执行速度     ─────────┼──────── 慢 ────   快   ──┼──── 本地优势
  代码可见性   ─────────┼──────── 受限 ──   完整 ──┼──── 本地优势  
  协议开销     ─────────┼──────── 有  ────  无   ──┼──── 本地优势
  修复成功率   ─────────┼──────── 高  ────  中低 ──┼──── 需更强模型
  可定制性     ─────────┼──────── 低  ────  高   ──┼──── 开源可控
```

**核心结论**：本地实现的最大短板是 AI 模型能力，最大优势是速度、代码可访问性和可定制性。如果接入更强的大模型（如 Claude API），差距可以大幅缩小。
